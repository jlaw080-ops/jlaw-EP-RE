# 09. 심화 — 요금체계(Tariff)와 VE 경제성

> **VE 경제성 검토를 EnergyPlus 안에서 끝낼 수 있습니다.**
> 에너지소요량을 뽑아 엑셀로 넘기는 대신, 요금 계산과 생애주기비용까지
> 시뮬레이션 내부에서 처리하는 방법입니다.
> 근거: `InputOutputReference` 3장 (p2841~2893), `EngineeringReference` (p1784~1795)

---

## 9-1. 경제성 관련 객체 전체 (3그룹)

| 그룹 | 객체 | 용도 |
|---|---|---|
| **공사비 산정** | `ComponentCost:Adjustments`<br>`ComponentCost:Reference`<br>`ComponentCost:LineItem` | 초기 투자비. **시뮬레이션에서 계산된 기기 용량·면적을 그대로 사용** |
| **요금 계산** | `UtilityCost:Tariff`<br>`UtilityCost:Qualify`<br>`UtilityCost:Charge:Simple`<br>`UtilityCost:Charge:Block`<br>`UtilityCost:Ratchet`<br>`UtilityCost:Variable`<br>`UtilityCost:Computation` | 월별 전기·가스요금 |
| **생애주기비용** | `LifeCycleCost:Parameters`<br>`LifeCycleCost:RecurringCosts`<br>`LifeCycleCost:NonrecurringCost`<br>`LifeCycleCost:UsePriceEscalation`<br>`LifeCycleCost:UseAdjustment` | LCC / 투자회수 |
| 통화 | `CurrencyType` | 통화 기호 |

> **공사비 산정이 시뮬레이션 결과와 연동된다는 점이 중요합니다.** 공식 문서 표현:
> *"it allows using results calculated during a simulation such as equipment sizes and
> surface areas."* 즉 자동 사이징으로 결정된 냉동기 용량에 단가를 곱해 투자비를
> 산출할 수 있습니다. **VE 대안별로 용량이 달라질 때 투자비가 자동으로 따라옵니다.**
>
> 단, 공식 문서도 한계를 명시합니다 —
> *"The cost estimating capabilities are not comprehensive and are not intended to
> duplicate all the types of analyses included in cost estimating software."*
> 적산 프로그램을 대체하는 것이 아니라, **대안 비교용 상대 비용**을 얻는 도구입니다.

# 제1부. 요금체계 (Tariff)

## 9-2. 기본 개념 — 변수와 계층

### 변수(Variable) = 12개 숫자의 묶음

요금 계산의 모든 값은 **월별 12개 숫자를 담은 변수**입니다. 배열이라고 생각하면 됩니다.

| 월 | Electric Energy Use |
|---|---|
| January | 12143 |
| February | 13454 |
| … | … |

`UtilityCost:Charge:*` 객체의 **이름 자체가 변수 이름**이 됩니다.
그 변수를 다른 요금 항목의 입력으로 다시 쓸 수 있습니다.

### ★ 요금 계층 구조 — 자동으로 합산됩니다

```
EnergyCharges  +  DemandCharges  +  ServiceCharges
        ↓
      Basis  +  Adjustments  +  Surcharges
        ↓
     Subtotal  +  Taxes
        ↓
       Total          ← 해당 에너지원의 월 요금 총액
```

같은 카테고리에 배정된 항목은 **자동으로 더해집니다.**
`UtilityCost:Computation` 을 쓰지 않으면 이 합산이 자동 수행됩니다.

**각 카테고리 자체도 변수이므로 다른 항목의 입력으로 쓸 수 있습니다.**
부가세처럼 "Subtotal의 x%"인 항목이 이 방식으로 표현됩니다.

```idf
UtilityCost:Charge:Simple,
  TaxOfFivePercent,   !- Charge Variable Name
  TariffExample1,     !- Tariff Name
  Subtotal,           !- Source Variable     ← 카테고리를 입력으로 사용
  Annual,             !- Season
  Taxes,              !- Category Variable Name
  0.05;               !- Cost Per Unit Value or Variable Name
```

> 중간 계산에만 쓰고 총액에 포함시키지 않을 항목은 **`NotIncluded`** 카테고리에 배정합니다.

### 가장 단순한 예 — kWh당 8센트 정액

```idf
UtilityCost:Tariff,
  TariffExample1,         !- Name
  Electricity:Facility,   !- Output Meter Name
  kWh;                    !- Conversion Factor Choice

UtilityCost:Charge:Simple,
  ChargeExample1,         !- Charge Variable Name
  TariffExample1,         !- Tariff Name
  totalEnergy,            !- Source Variable
  Annual,                 !- Season
  EnergyCharges,          !- Category Variable Name
  0.08;                   !- Cost Per Unit Value or Variable Name
```

공식 문서가 밝힌 설계 목표: *"make simple tariffs easy to model and
complex tariffs possible to model."*

## 9-3. ★ 계시별(TOU) 요금 — 국내 요금제의 핵심

`UtilityCost:Tariff` 의 스케줄 필드로 시간대·계절을 정의하면,
**EnergyPlus가 변수를 자동 생성**합니다.

### Time of Use Period Schedule — 하루 중 시간대

스케줄 값(정수)과 의미:

| 값 | 기간 | 국내 대응 |
|---|---|---|
| **1** | Peak | **최대부하** |
| **2** | Shoulder | (국내 3단계 요금제에서는 미사용) |
| **3** | OffPeak | **경부하** |
| **4** | MidPeak | **중간부하** |

자동 생성되는 변수:

```
peakEnergy      peakDemand
shoulderEnergy  shoulderDemand
offPeakEnergy   offPeakDemand
midPeakEnergy   midPeakDemand
```

특수 변수(한 기간의 수요가 다른 기간을 초과한 부분만 담음, 초과하지 않은 달은 0):

```
PeakExceedsOffPeak    OffPeakExceedsPeak
PeakExceedsMidPeak    MidPeakExceedsPeak
PeakExceedsShoulder   ShoulderExceedsPeak
```

> Period Schedule을 지정하지 않으면 **peak/offPeak/midPeak/shoulder 변수가 아예
> 정의되지 않습니다.** 계시별 요금을 모델링하려면 반드시 넣어야 합니다.

### Season Schedule — 계절

| 값 | 계절 |
|---|---|
| 1 | Winter |
| 2 | Spring |
| 3 | Summer |
| 4 | Autumn |

자동 생성 변수: `isWinter` / `isNotWinter` / `isSpring` / `isNotSpring` /
`isSummer` / `isNotSummer` / `isAutumn` / `isNotAutumn`
(해당 계절인 달은 1, 아닌 달은 0)

### ★ 반드시 지켜야 할 제약

> *"The change in the season schedule must occur at the same time as the change in the
> Monthly Schedule. In other words, a season must end at the same time as a billing month."*

**계절 경계와 검침월 경계가 일치해야 합니다.** 불일치하면 오류가 발생합니다.

`Month Schedule Name` 은 보통 비워 두면 월 경계(매월 1일 0시)가 자동 적용됩니다.
2개월 주기 검침이나 계절 단위 일괄 청구 같은 특수 체계일 때만 직접 지정합니다.

## 9-4. 국내 전기요금(일반용/산업용) 구현 설계안

위 구조를 국내 요금제에 대응시키면 이렇게 됩니다.

| 국내 요금 항목 | EnergyPlus 카테고리 | 사용 객체 |
|---|---|---|
| **기본요금** (피크 kW 기준) | `DemandCharges` | `Charge:Simple` (source: `peakDemand` 등) |
| **전력량요금** (계시별 단가) | `EnergyCharges` | `Charge:Simple` × 시간대·계절 조합별 |
| 기후환경요금 | `Adjustments` | `Charge:Simple` (source: `totalEnergy`) |
| 연료비조정액 | `Adjustments` | `Charge:Simple` |
| **전력산업기반기금** | `Taxes` | `Charge:Simple` (source: `Subtotal`) |
| **부가가치세** | `Taxes` | `Charge:Simple` (source: `Subtotal`) |

계절은 **여름(Summer) / 겨울(Winter) / 봄가을(Spring + Autumn)** 로 매핑하고,
시간대는 **최대부하(1) / 중간부하(4) / 경부하(3)** 로 매핑합니다.

```
예: 여름 최대부하 전력량요금
UtilityCost:Charge:Simple,
  SummerPeakEnergy,     !- Charge Variable Name
  KEPCO_General_B,      !- Tariff Name
  peakEnergy,           !- Source Variable     ← 자동 생성 변수
  Summer,               !- Season
  EnergyCharges,        !- Category Variable Name
  <단가>;               !- Cost Per Unit Value
```

> **주의 — 아래는 제가 공식 문서의 구조에서 유도한 설계안이며, 실제 요금제 검증은
> 사용자님이 하셔야 합니다.**
>
> 1. **현행 한전 요금표를 직접 확인하십시오.** 단가·시간대 구분·계절 구분은 매년
>    바뀝니다. 이 문서는 "어떤 객체로 표현하는가"만 다룹니다.
> 2. **역률요금·계약전력 초과부담금 등 국내 특유 항목**은 위 구조로 직접 표현되지
>    않습니다. `UtilityCost:Computation` 으로 별도 계산식을 써야 할 수 있습니다
>    (복잡 요금 모델링: IORef p2869).
> 3. 구현 후 **알고 있는 실제 고지서와 대조 검증**하십시오. 요금 모델은 틀려도
>    오류가 나지 않고 그냥 틀린 숫자를 냅니다.

## 9-5. 블록 요금과 기타

| 객체 | 용도 |
|---|---|
| `UtilityCost:Charge:Block` | **누진·블록 요금** (주택용 누진제) |
| `UtilityCost:Ratchet` | 과거 피크를 기준으로 현재 수요요금을 끌어올리는 조항 |
| `UtilityCost:Qualify` | 이 요금제 적용 자격 조건(사용량 범위 등) |
| `UtilityCost:Variable` | 사용자 정의 월별 값 |
| `UtilityCost:Computation` | **직접 계산식 작성** (간단한 프로그래밍 언어) |

`UtilityCost:Qualify` 를 쓰면 **여러 요금제를 동시에 정의하고 조건에 맞는 것을
자동 선택**하게 할 수 있습니다. "어떤 요금제가 유리한가"를 비교하는 VE 검토에 유용합니다.

예제는 IORef p2859 (`UtilityCost:Tariff Examples`),
결과 리포트는 IORef p2868 (`Economic Results Summary Report`) 에 있습니다.

# 제2부. 생애주기비용 (LCC)

## 9-6. 객체 구성

| 객체 | 입력 내용 |
|---|---|
| **`LifeCycleCost:Parameters`** | 분석 기간, 할인율, 할인 방식, 기준 시점 등 |
| `LifeCycleCost:RecurringCosts` | **반복 비용** (유지관리비, 정기 교체비) |
| `LifeCycleCost:NonrecurringCost` | **일시 비용** (초기 투자비, 대수선) |
| `LifeCycleCost:UsePriceEscalation` | **에너지 가격 상승률** (연도별·에너지원별) |
| `LifeCycleCost:UseAdjustment` | 사용량 조정 |

계산 이론은 EngRef p1793 (`Life-Cycle Cost Computations`) 입니다.

## 9-7. 내장 데이터셋 — 그리고 국내 적용 시 교체 대상

설치 폴더 `DataSets\` 에 **미국 기준 에너지 가격 상승률 데이터**가 들어 있습니다.

```
LCCusePriceEscalationDataSet2012.idf  …  LCCusePriceEscalationDataSet2022.idf
```

(소스 저장소 기준 `datasets/` — [`01-전체구조.md`](01-전체구조.md) 참조)

> **이 데이터는 미국 NIST/DOE 기준입니다.** 국내 VE 검토에 그대로 쓰면 안 됩니다.
> 한국 전력·가스 요금 추이와 물가상승률로 **`LifeCycleCost:UsePriceEscalation` 을
> 직접 작성**하셔야 합니다. 객체 형식만 가져오고 숫자는 교체하는 방식입니다.

## 9-8. 결과 확인

| 리포트 | 활성화 방법 |
|---|---|
| Economic Results Summary | `Output:Table:SummaryReports` (AllSummary에 포함) |
| **Construction Cost Estimate Summary** | `Output:Table:SummaryReports` 에 `ComponentCostEconomicsSummary` |
| Life-Cycle Cost Report | `LifeCycleCost:Parameters` 가 있으면 자동 생성 |

이 리포트들도 **SQLite DB의 `TabularDataWithStrings` 에 들어갑니다.**
따라서 케이스 100개의 LCC를 SQL 한 번으로 비교할 수 있습니다
([`04-자동화.md`](04-자동화.md) 4-3절).

```sql
SELECT RowName, ColumnName, Value, Units FROM TabularDataWithStrings
WHERE ReportName LIKE '%Life%Cycle%';
```

## 9-9. VE 검토 파이프라인에 넣는 방법

[`04-자동화.md`](04-자동화.md) 4-6절의 파이프라인에 경제성을 결합하면 이렇게 됩니다.

```
[1] 기준 모델 + UtilityCost:* + LifeCycleCost:* 객체 포함
         │
[2] 케이스 생성 — 단열두께 × 창호U값 × 설비효율 × 신재생 용량
         │        (기기 용량은 자동 사이징에 맡기면 ComponentCost가 따라옴)
[3] 병렬 실행
         │
[4] 성공 판정  (.sql 존재 → .end → Errors → Unmet Hours)
         │
[5] SQL 집계 — 한 번의 질의로 아래를 동시에 뽑음
         │     · 연간 1차에너지소요량      (AnnualBuildingUtilityPerformanceSummary)
         │     · 에너지자립률 근거          (Electric Loads Satisfied)
         │     · 연간 에너지비용            (Economic Results Summary)
         │     · 초기 투자비                (Construction Cost Estimate Summary)
         │     · 생애주기비용               (Life-Cycle Cost Report)
         │
[6] VE 판정 — 투자비 대비 절감액, 투자회수기간, LCC 최소점
```

> **이 구조의 장점**: 에너지 결과와 비용 결과가 **같은 시뮬레이션에서 일관되게**
> 나옵니다. 엑셀로 옮기는 과정에서 생기는 전제 불일치(기기 용량, 면적, 운전시간)가
> 사라집니다. VE 보고서의 신뢰도가 올라가는 실질적 이유입니다.
>
> **한계도 분명합니다**: 국내 요금제·물가 데이터를 직접 구축해야 하고, 적산 수준의
> 공사비 정밀도는 나오지 않습니다. **대안 간 상대 비교**에 쓰고, 절대 금액은
> 적산 자료로 보완하는 것이 맞습니다.
