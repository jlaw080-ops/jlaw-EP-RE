# 09. 심화 — 요금체계(Tariff)와 VE 경제성

> **VE 경제성 검토를 EnergyPlus 안에서 끝낼 수 있습니다.**
> 에너지소요량을 뽑아 엑셀로 넘기는 대신, 요금 계산과 생애주기비용까지
> 시뮬레이션 내부에서 처리하는 방법입니다.
> 근거: `InputOutputReference` 3장 (p2841~2893), `EngineeringReference` (p1784~1795)

---

## 9-1. 경제성 관련 객체 전체 (3그룹)

| 그룹 | 객체 | 용도 |
|---|---|---|
| **공사비 산정** | `ComponentCost:Adjustments`<br>`ComponentCost:Reference`<br>`ComponentCost:LineItem` | 초기 투자비. **시뮬레이션에서 계산된 기기 용량·면적을 그대로 사용** |
| **요금 계산** | `UtilityCost:Tariff`<br>`UtilityCost:Qualify`<br>`UtilityCost:Charge:Simple`<br>`UtilityCost:Charge:Block`<br>`UtilityCost:Ratchet`<br>`UtilityCost:Variable`<br>`UtilityCost:Computation` | 월별 전기·가스요금 |
| **생애주기비용** | `LifeCycleCost:Parameters`<br>`LifeCycleCost:RecurringCosts`<br>`LifeCycleCost:NonrecurringCost`<br>`LifeCycleCost:UsePriceEscalation`<br>`LifeCycleCost:UseAdjustment` | LCC / 투자회수 |
| 통화 | `CurrencyType` | 통화 기호 |

> **공사비 산정이 시뮬레이션 결과와 연동된다는 점이 중요합니다.** 공식 문서 표현:
> *"it allows using results calculated during a simulation such as equipment sizes and
> surface areas."* 즉 자동 사이징으로 결정된 냉동기 용량에 단가를 곱해 투자비를
> 산출할 수 있습니다. **VE 대안별로 용량이 달라질 때 투자비가 자동으로 따라옵니다.**
>
> 단, 공식 문서도 한계를 명시합니다 —
> *"The cost estimating capabilities are not comprehensive and are not intended to
> duplicate all the types of analyses included in cost estimating software."*
> 적산 프로그램을 대체하는 것이 아니라, **대안 비교용 상대 비용**을 얻는 도구입니다.

# 제1부. 요금체계 (Tariff)

## 9-2. 기본 개념 — 변수와 계층

### 변수(Variable) = 12개 숫자의 묶음

요금 계산의 모든 값은 **월별 12개 숫자를 담은 변수**입니다. 배열이라고 생각하면 됩니다.

| 월 | Electric Energy Use |
|---|---|
| January | 12143 |
| February | 13454 |
| … | … |

`UtilityCost:Charge:*` 객체의 **이름 자체가 변수 이름**이 됩니다.
그 변수를 다른 요금 항목의 입력으로 다시 쓸 수 있습니다.

### ★ 요금 계층 구조 — 자동으로 합산됩니다

```
EnergyCharges  +  DemandCharges  +  ServiceCharges
        ↓
      Basis  +  Adjustments  +  Surcharges
        ↓
     Subtotal  +  Taxes
        ↓
       Total          ← 해당 에너지원의 월 요금 총액
```

같은 카테고리에 배정된 항목은 **자동으로 더해집니다.**
`UtilityCost:Computation` 을 쓰지 않으면 이 합산이 자동 수행됩니다.

**각 카테고리 자체도 변수이므로 다른 항목의 입력으로 쓸 수 있습니다.**
부가세처럼 "Subtotal의 x%"인 항목이 이 방식으로 표현됩니다.

```idf
UtilityCost:Charge:Simple,
  TaxOfFivePercent,   !- Charge Variable Name
  TariffExample1,     !- Tariff Name
  Subtotal,           !- Source Variable     ← 카테고리를 입력으로 사용
  Annual,             !- Season
  Taxes,              !- Category Variable Name
  0.05;               !- Cost Per Unit Value or Variable Name
```

> 중간 계산에만 쓰고 총액에 포함시키지 않을 항목은 **`NotIncluded`** 카테고리에 배정합니다.

### 가장 단순한 예 — kWh당 8센트 정액

```idf
UtilityCost:Tariff,
  TariffExample1,         !- Name
  Electricity:Facility,   !- Output Meter Name
  kWh;                    !- Conversion Factor Choice

UtilityCost:Charge:Simple,
  ChargeExample1,         !- Charge Variable Name
  TariffExample1,         !- Tariff Name
  totalEnergy,            !- Source Variable
  Annual,                 !- Season
  EnergyCharges,          !- Category Variable Name
  0.08;                   !- Cost Per Unit Value or Variable Name
```

공식 문서가 밝힌 설계 목표: *"make simple tariffs easy to model and
complex tariffs possible to model."*

## 9-3. ★ 계시별(TOU) 요금 — 국내 요금제의 핵심

`UtilityCost:Tariff` 의 스케줄 필드로 시간대·계절을 정의하면,
**EnergyPlus가 변수를 자동 생성**합니다.

### Time of Use Period Schedule — 하루 중 시간대

스케줄 값(정수)과 의미:

| 값 | 기간 | 국내 대응 |
|---|---|---|
| **1** | Peak | **최대부하** |
| **2** | Shoulder | (국내 3단계 요금제에서는 미사용) |
| **3** | OffPeak | **경부하** |
| **4** | MidPeak | **중간부하** |

자동 생성되는 변수:

```
peakEnergy      peakDemand
shoulderEnergy  shoulderDemand
offPeakEnergy   offPeakDemand
midPeakEnergy   midPeakDemand
```

특수 변수(한 기간의 수요가 다른 기간을 초과한 부분만 담음, 초과하지 않은 달은 0):

```
PeakExceedsOffPeak    OffPeakExceedsPeak
PeakExceedsMidPeak    MidPeakExceedsPeak
PeakExceedsShoulder   ShoulderExceedsPeak
```

> Period Schedule을 지정하지 않으면 **peak/offPeak/midPeak/shoulder 변수가 아예
> 정의되지 않습니다.** 계시별 요금을 모델링하려면 반드시 넣어야 합니다.

### Season Schedule — 계절

| 값 | 계절 |
|---|---|
| 1 | Winter |
| 2 | Spring |
| 3 | Summer |
| 4 | Autumn |

자동 생성 변수: `isWinter` / `isNotWinter` / `isSpring` / `isNotSpring` /
`isSummer` / `isNotSummer` / `isAutumn` / `isNotAutumn`
(해당 계절인 달은 1, 아닌 달은 0)

### ★ 반드시 지켜야 할 제약

> *"The change in the season schedule must occur at the same time as the change in the
> Monthly Schedule. In other words, a season must end at the same time as a billing month."*

**계절 경계와 검침월 경계가 일치해야 합니다.** 불일치하면 오류가 발생합니다.

`Month Schedule Name` 은 보통 비워 두면 월 경계(매월 1일 0시)가 자동 적용됩니다.
2개월 주기 검침이나 계절 단위 일괄 청구 같은 특수 체계일 때만 직접 지정합니다.

### 요금 항목 대응

| 국내 요금 항목 | 값 | EnergyPlus 카테고리 | Source Variable |
|---|---|---|---|
| **기본요금** | 8,320 원/kW | `DemandCharges` | `TotalDemand` |
| **전력량요금** | 계절×시간대 9종 | `EnergyCharges` | `PeakEnergy` / `MidPeakEnergy` / `OffPeakEnergy` |
| **기후환경요금** | 9.0 원/kWh | `Adjustment` | `TotalEnergy` |
| **연료비조정액** | 5.0 원/kWh | `Adjustment` | `TotalEnergy` |
| **전력산업기반기금** | 2.7% | `Taxes` | `Subtotal` |

계층이 국내 청구 구조와 정확히 맞습니다.

```
Subtotal = EnergyCharges + DemandCharges + Adjustment   =  전기요금

```

### 전력량요금 실제 요율 (원/kWh)

| 계절 | 경부하 | 중간부하 | 최대부하 |
|---|---:|---:|---:|
| 여름철 (6~8월) | 87.3 | 140.2 | **222.3** |
| 봄·가을철 (3~5, 9~10월) | 87.3 | 109.8 | 140.5 |
| 겨울철 (11~2월) | 94.3 | 140.4 | 197.9 |

### 계절·시간대 스케줄 매핑

| 한전 | EnergyPlus 코드 |
|---|---|
| 경부하 | **3** OffPeak |
| 중간부하 | **4** MidPeak |
| 최대부하 | **1** Peak |
| 겨울철 | **1** Winter |
| 봄·가을철 | **2** Spring + **4** Autumn |
| 여름철 | **3** Summer |

시간대 구분은 계절별로 다릅니다.

```
여름철·봄가을철   경 22-08 / 중 08-15, 21-22 / 최 15-21
겨울철            경 22-08 / 중 08-09, 12-16, 19-22 / 최 09-12, 16-19
```

그래서 `Schedule:Compact` 를 다섯 구간(1~2월, 3~5월, 6~8월, 9~10월, 11~12월)으로
나눕니다. 계절 경계가 **검침월 경계와 일치**해야 하는 EnergyPlus 제약도 함께 만족합니다.

> **봄·가을철 주의**: 한전은 한 계절이지만 EnergyPlus 는 Spring/Autumn 으로 나뉩니다.
> 같은 단가를 **두 번 선언**해야 합니다(`Season` 필드에 `Spring`, `Fall` 각각).
> `Charge:Simple` 의 Season 선택지는 `Fall` 인데 스케줄 코드값은 `Autumn` 입니다
> — EnergyPlus 자체의 용어 불일치이므로 헷갈리지 마십시오.

### ★ Output Meter 선택 — ZEB 검토에서 결정적

```idf
UtilityCost:Tariff,
  KEPCO_GeneralB_HVA_Opt2,
  ElectricityPurchased:Facility,  !- Output Meter Name  ← 이것
  ...
```

| 계량기 | 의미 |
|---|---|
| `Electricity:Facility` | 건물이 **소비한** 전력 전체 |
| **`ElectricityPurchased:Facility`** | **계통에서 사들인** 전력 |

신재생 자가발전이 있으면 두 값이 다릅니다. 요금은 **사들인 전력**에 붙습니다.

> `Electricity:Facility` 를 쓰면 **자가발전분까지 요금을 매겨 절감액이 0 으로 나옵니다.**
> PV·연료전지 경제성 검토가 전부 무의미해집니다. 반드시 `Purchased` 를 쓰십시오.

## 9-4-2. 반영하지 못한 국내 규칙

### ★ 요금적용전력 규칙 — 가장 큰 차이

한전 기본요금은 **요금적용전력**에 붙는데, 그 값은

```
max( 당월 최대수요전력,
     직전 11개월 중 최대수요전력,
     계약전력의 30% )
```

입니다. 이 IDF 는 **당월 최대수요전력만** 씁니다.

- 과거 피크가 당월보다 높은 달은 **기본요금이 과소 계산**됩니다
- 직전 피크를 끌어오는 조항은 `UtilityCost:Ratchet` 으로 근사할 수 있습니다
- "직전 11개월 중 최대"와 "계약전력 30% 하한"을 동시에 만족시키려면
  `UtilityCost:Computation` 으로 계산식을 직접 써야 합니다

> **피크 저감(수요관리) VE 검토를 할 때는 이 한계가 결과를 바꿉니다.**
> 빙축열·ESS 같이 피크를 깎는 대안은 기본요금 절감이 핵심 효과인데,
> 요금적용전력 규칙을 넣지 않으면 그 효과가 과대평가됩니다.

### 그 외

| 항목 | 내용 | 영향 |
|---|---|---|
| 원단위 절사·사사오입 | 부가세 원미만 4사5입, 기금 10원미만 절사. EnergyPlus 는 안 함 | 월 수 원 — VE 비교에 무영향 |
| 역률요금 | 지상·진상 역률 가감. EnergyPlus 는 역률을 모름 | 별도 산정해 가산 |
| 주말·휴일 할인 | 산업용(을)에 신설. 일반용(을)엔 해당 없음 | 다른 종별 적용 시 `For: Weekends` 블록 필요 |
| 윤년 | `Through: 2/28` 이라 2/29 가 다음 블록으로 넘어감 | TMY/TRY 는 비윤년이라 무영향. AMY 윤년 해석 시 2/29 로 수정 |

### 부가요금 값의 신뢰도 — 반드시 확인할 것

`energinno-DB` 가 기록한 출처·신뢰도를 그대로 옮깁니다.

| 항목 | 값 | 출처 | 주의 |
|---|---|---|---|
| 기후환경요금 | 9.0 원/kWh | 2023-05-16 요금표 | **2024-01-01 이후 요금표엔 단가가 인쇄되지 않음.** 2026년에도 9원이라는 **보도만** 있고 한전 공식 확인 안 됨 → 한전ON 확인 |
| 연료비조정단가 | 5.0 원/kWh | 2026년 4분기 **보도** | **분기마다 바뀜.** 검토 시점 값으로 교체. 2022년 4분기 이후 확인된 시점은 모두 상한인 +5원 |
| 전력산업기반기금 | 2.7% | 2025-04-01 요금표 주석 | 2025-07-01부 3.2% → 2.7% 인하 |

> **검증 권고**: 알고 있는 실제 고지서와 대조하십시오. 특히 기본요금은 요금적용전력
> 규칙 때문에 차이가 날 수 있으니, 그 차이가 설명되는지 확인하십시오.

## 9-4-3. 다른 종별로 바꾸는 방법

`energinno-DB` 에 16개 계약종별이 모두 있습니다.

| `rate_structure` | 종별 | 스케줄 필요 여부 |
|---|---|---|
| `time_of_use` | 일반용(갑)Ⅱ·(을), 산업용(갑)Ⅱ·(을), 교육용(을), 주택용 계시별 | **계절 + 시간대 둘 다** |
| `seasonal` | 교육용(갑), 일반용(갑)Ⅰ, 산업용(갑)Ⅰ, 심야전력 | 계절만 |
| `progressive` | 주택용전력 | 누진 → `Charge:Block` |
| `flat` | 가로등 | 없음 |
| `mixed` | 농사용전력 | 조합 |

`time_of_use` 종별은 이 IDF 의 스케줄을 그대로 쓰고 **요율 숫자와 기본요금만**
바꾸면 됩니다. 단 **시간대 구분이 종별마다 다를 수 있으니** 해당 요금표의
`definitions.time_zones` 를 확인하고, 바꿨으면 `check_schedule.py` 로 재검증하십시오.

`progressive`(주택용 누진제)는 `UtilityCost:Charge:Block` 이 필요합니다 — 9-5절 참조.

| 지열 히트펌프 | 1,381,000 원/kW | 외부 집계 |

### ★ 왜 두 경로로 나뉘는가 — `ComponentCost:LineItem` 의 한계

`Line Item Type` 선택지는 **11개뿐**입니다. IDD 주석이 이유를 밝힙니다 —
*"extend choice-keys as Cases are added to code"*. 코드에 `case` 가 추가된 것만
쓸 수 있습니다.

```
General                       Construction
Coil:DX                       Coil:Cooling:DX
Coil:Cooling:DX:SingleSpeed   Coil:Heating:Fuel
Chiller:Electric              Daylighting:Controls
Shading:Zone:Detailed         Lights
Generator:Photovoltaic        ← 신재생은 이 하나뿐
```

**연결되지 않는 신재생 설비** — 전부 키가 없습니다.

| 설비 | 객체 |
|---|---|
| 지열 히트펌프 | `HeatPump:PlantLoop:EIR:*`, `HeatPump:WaterToWater:*` |
| 연료전지 | `Generator:FuelCell` |
| ESS | `ElectricLoadCenter:Storage:*` |
| 태양열 | `SolarCollector:*` |
| 풍력 | `Generator:WindTurbine` |

자동 사이징 결과와 연동되는 것(용량이 바뀌면 투자비가 따라옴)은 다음뿐입니다.

| Line Item Type | 수량 근거 |
|---|---|
| `Coil:DX` / `Coil:Cooling:DX` / `:SingleSpeed` | `RatedTotCap` [kW] |
| `Coil:Heating:Fuel` | `NominalCapacity` [kW] |
| `Chiller:Electric` | `NomCap` [kW] |
| `Construction` / `Shading:Zone:Detailed` | 면적 [m²] |
| `Lights` | 존 조명 [kW] |
| `Generator:Photovoltaic` | 면적 × 효율 [kW] (**사이징 아님**) |

### 경로 ① 태양광 — EnergyPlus 내장

```
idf/cost/신재생_투자비_태양광.idf
```

**제약 두 가지를 반드시 아셔야 합니다.**

**(1) `PhotovoltaicPerformance:Simple` 모델 전용입니다.**
소스가 명시합니다 — *"Generator:Photovoltaic, only available for model type
PhotovoltaicPerformance:Simple"* (`CostEstimateManager.cc`).

> `Generator:PVWatts`, `PhotovoltaicPerformance:Sandia`,
> `:EquivalentOne-Diode` 를 쓰면 **투자비가 연결되지 않습니다.**
> 발전량 정밀도를 택하면 비용 연결을 잃고, 비용 연결을 택하면 Simple 모델을
> 써야 합니다. **둘을 동시에 얻을 수 없습니다.**
>
> [`10-에너지분석로직.md`](10-에너지분석로직.md) 5-2절에서 `Generator:PVWatts` 를
> "가장 빠른 경로"로 권했는데, **투자비까지 연결하려면 그 권고가 맞지 않습니다.**

**(2) PV 용량은 자동 사이징되지 않습니다.** 소스 실측 산식:

```
정격용량[kW] = 집열면적[m²] × 모듈효율 × Zone승수
집열면적     = 설치면 면적 × Fraction of Surface Area with Active Solar Cells
```

목표 용량은 면적을 역산해 맞춥니다. 예) 100 kW, 효율 0.20, 활성면적비 0.90
→ 집열면적 500 m², 설치면 면적 556 m².

> VE 관점에서는 이게 오히려 유리합니다. 설치 가능 면적을 바꾸면 용량과 투자비가
> 함께 따라오므로 **"면적 제약 하 최적 용량" 검토**가 됩니다.

**턴키 단가에 간접비를 얹지 마십시오.** `energinno-DB` 가 이 단가를
`턴키(합계)`(설치 완료 기준)로 기록했습니다. `ComponentCost:Adjustments` 의
설계·감리비·시공사 이윤·예비비를 추가하면 **중복 계상**입니다. 전부 공란으로 둡니다.

### 경로 ② 그 외 설비 — 외부 집계

```bash
python3 scripts/cost/estimate_cost.py <결과.sql> <장비단가.json> [옵션]
```

자동 사이징 결과가 `.sql` 의 `ComponentSizes` 테이블
(`CompType`, `CompName`, `Description`, `Value`, `Units`)에 들어가므로,
거기서 용량을 읽어 단가를 곱합니다. **케이스마다 용량이 자동 반영**되므로
파라메트릭 VE 검토에 맞습니다.

> `General` 타입 + `Quantity` 로 IDF 안에 넣을 수도 있지만, 용량을 사람이 직접
> 적어야 해서 파라메트릭 자동화가 깨집니다. 그래서 외부 집계를 택했습니다.

### ★ 중복 계상을 막는 두 가지 옵션 — 개발 중 실제로 걸린 문제

**(1) `--fuelcell pafc|pemfc|sofc` — 지정하지 않으면 제외합니다**

EnergyPlus 의 `Generator:FuelCell` 은 **PAFC/PEMFC/SOFC 를 구분하지 않습니다.**
성능 파라미터로만 표현되므로 종류를 자동 판별할 수 없습니다.

> 처음 구현에서 100 kW 연료전지 하나가 세 종류 모두에 매칭되어 **142억원**으로
> 계산됐습니다(실제 100억). 종류를 지정하지 않으면 제외하고 경고하도록 고쳤습니다.
> 단가가 kW당 1,200만~1억원이라 **종류를 틀리면 투자비가 8배 달라집니다.**

**(2) `--geo-sum` — 지열은 기본이 "큰 쪽(max)"입니다**

지열 히트펌프는 보통 한 기기가 냉난방을 겸하는데, EnergyPlus 는 난방·냉방 용량을
각각 보고합니다. 더하면 2배 계상입니다.

> 난방 120 kW + 냉방 150 kW 인 모델에서 합산하면 270 kW(3.7억원),
> 큰 쪽을 쓰면 150 kW(2.1억원)입니다. **기본은 max** 이고, 냉방기·난방기가
> 물리적으로 별개인 모델이면 `--geo-sum` 을 씁니다.
> 어느 쪽으로 집계했는지 출력에 항상 표시되고, 합산값도 함께 알려줍니다.

### 합산 시 주의

태양광은 경로 ①(EnergyPlus 내장)이, 나머지는 경로 ②(외부 집계)가 처리합니다.
**총 투자비는 두 결과를 합산**해야 합니다.

```
총 투자비 = Construction Cost Estimate Summary (태양광 + 기존 설비)
          + estimate_cost.py 결과 (지열 · 연료전지 · ESS)
```

스크립트는 태양광을 일부러 제외하므로 중복되지 않습니다.

> **부가가치세**: `energinno-DB` 가 "부가세 포함 여부가 화면에 없다"고 기록했습니다.
> 제안서에 쓸 때 확인하십시오.

## 9-5. 블록 요금과 기타

| 객체 | 용도 |
|---|---|
| `UtilityCost:Charge:Block` | **누진·블록 요금** (주택용 누진제) |
| `UtilityCost:Ratchet` | 과거 피크를 기준으로 현재 수요요금을 끌어올리는 조항 |
| `UtilityCost:Qualify` | 이 요금제 적용 자격 조건(사용량 범위 등) |
| `UtilityCost:Variable` | 사용자 정의 월별 값 |
| `UtilityCost:Computation` | **직접 계산식 작성** (간단한 프로그래밍 언어) |

`UtilityCost:Qualify` 를 쓰면 **여러 요금제를 동시에 정의하고 조건에 맞는 것을
자동 선택**하게 할 수 있습니다. "어떤 요금제가 유리한가"를 비교하는 VE 검토에 유용합니다.

예제는 IORef p2859 (`UtilityCost:Tariff Examples`),
결과 리포트는 IORef p2868 (`Economic Results Summary Report`) 에 있습니다.

## 9-6. 객체 구성

| 객체 | 입력 내용 |
|---|---|

## 9-9. VE 검토 파이프라인에 넣는 방법

[`04-자동화.md`](04-자동화.md) 4-6절의 파이프라인에 경제성을 결합하면 이렇게 됩니다.

```
[1] 기준 모델 + UtilityCost:* + LifeCycleCost:* 객체 포함
         │
[2] 케이스 생성 — 단열두께 × 창호U값 × 설비효율 × 신재생 용량
         │        (기기 용량은 자동 사이징에 맡기면 ComponentCost가 따라옴)
[3] 병렬 실행
         │
[4] 성공 판정  (.sql 존재 → .end → Errors → Unmet Hours)
         │
[5] SQL 집계 — 한 번의 질의로 아래를 동시에 뽑음
         │     · 연간 1차에너지소요량      (AnnualBuildingUtilityPerformanceSummary)
         │     · 에너지자립률 근거          (Electric Loads Satisfied)
         │     · 연간 에너지비용            (Economic Results Summary)
         │     · 초기 투자비                (Construction Cost Estimate Summary)
         │     · 생애주기비용               (Life-Cycle Cost Report)
         │
[6] VE 판정 — 투자비 대비 절감액, 투자회수기간, LCC 최소점
```

> **이 구조의 장점**: 에너지 결과와 비용 결과가 **같은 시뮬레이션에서 일관되게**
> 나옵니다. 엑셀로 옮기는 과정에서 생기는 전제 불일치(기기 용량, 면적, 운전시간)가
> 사라집니다. VE 보고서의 신뢰도가 올라가는 실질적 이유입니다.
>
> **한계도 분명합니다**: 국내 요금제·물가 데이터를 직접 구축해야 하고, 적산 수준의
> 공사비 정밀도는 나오지 않습니다. **대안 간 상대 비교**에 쓰고, 절대 금액은
> 적산 자료로 보완하는 것이 맞습니다.
