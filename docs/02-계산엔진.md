# 02. 계산 엔진 — 알고리즘 추적 지도

> 모든 경로는 소스 저장소 기준이며, 줄 번호는 **v26.2.0 태그** 기준 실측값입니다.

## 2-1. 프로그램 진입점 — 어디서 시작하는가

`energyplus.exe`를 실행하면 아래 순서로 들어갑니다.

| 단계 | 파일 | 역할 |
|---|---|---|
| 1 | `src/EnergyPlus/main.cc` | 단 10줄. CLI 인자를 받아 넘기기만 함 |
| 2 | `src/EnergyPlus/api/EnergyPlusPgm.cc` | 실제 프로그램 본체 |
| 3 | `src/EnergyPlus/CommandLineInterface.cc` | 옵션 해석, 출력 파일 경로 결정 (49KB) |
| 4 | `src/EnergyPlus/SimulationManager.cc` | **시뮬레이션 총괄 — 핵심** (170KB) |

`main.cc`가 10줄뿐인 것은 중요한 설계입니다.
**엔진 본체가 `api/` 폴더 안에 라이브러리로 분리되어 있다는 뜻**이고,
이것이 뒤에 나오는 Python API / 웹서비스화의 기술적 근거가 됩니다.
(→ [`04-자동화.md`](04-자동화.md))

## 2-2. 시뮬레이션 루프 계층 — 시간이 흐르는 구조

`SimulationManager.cc` 의 `ManageSimulation()` (240번째 줄부터)가 전체를 돌립니다.
실제 루프 중첩 구조는 다음과 같습니다.

```
ManageSimulation()                                    ← 240줄
│
├─ [사이징 계산]  ManageSizing / ManageHVACSizingSimulation   ← 437줄
│      난방·냉방 부하 계산 → 기기 용량 자동 결정
│
└─ while (Available)                  ← 449줄  【환경(Environment) 루프】
   │    환경 = 설계일(Design Day) 1개 또는 연간 RunPeriod 1개
   │
   └─ while (DayOfSim < NumOfDayInEnvrn || WarmupFlag)   ← 511줄  【일(Day) 루프】
      │    WarmupFlag: 예비수렴(Warmup) 중인지 여부. 아래 2-3 참조
      │
      └─ for (HourOfDay = 1 … 24)                       ← 561줄  【시(Hour) 루프】
         │
         └─ for (TimeStep = 1 … TimeStepsInHour)        ← 569줄  【존 타임스텝 루프】
            │    TimeStepsInHour: IDF의 Timestep 객체값 (보통 4 또는 6)
            │
            ├─ Weather::ManageWeather()                 ← 608줄  기상데이터 읽기/보간
            └─ ManageHeatBalance()                      ← 612줄  ★ 열평형 계산 전체
```

**실무적 의미**: 연간 시뮬레이션 1회는
`365일 × 24시간 × 6 타임스텝 = 52,560회`의 열평형 계산을 수행합니다.
여기에 아래 Warmup 반복까지 더해집니다.
**왜 연간 해석이 수십 초~수 분 걸리는지**가 이 구조에서 설명됩니다.
웹서비스 설계 시 이 계산 시간이 결정적 제약이 됩니다.

## 2-3. Warmup — ZEB 해석에서 반드시 알아야 할 개념

위 구조에서 `WarmupFlag`가 중요합니다.
시뮬레이션 시작 시점에 건물 구조체(벽·바닥·슬래브)에 축열된 열량을 알 수 없으므로,
EnergyPlus는 **같은 첫날을 수렴할 때까지 반복 계산**합니다.
이 반복 구간의 결과는 **출력에 기록되지 않습니다**(`if (!WarmupFlag)` 조건, 522·531줄).

- 축열체가 큰 건물(콘크리트 구조, 패시브하우스 고단열)은 Warmup 반복이 많이 필요
- Warmup이 수렴하지 않으면 `.err` 파일에 경고가 남고, **결과 신뢰도가 떨어짐**
- 관련 입력 객체: `Building` 객체의 `Minimum Number of Warmup Days` / `Maximum ...`

> **VE 검토 실무 체크포인트**: 고단열·고축열 ZEB 모델에서 Warmup 경고를 무시하면
> 연간 에너지소요량이 과소/과대 평가됩니다. 결과 검증 시 `.err` 의 Warmup 항목을
> 자동으로 체크하는 로직을 넣는 것이 좋습니다. (→ [`04-자동화.md`](04-자동화.md))

## 2-4. 열평형 호출 계층도 — 소스에 박혀 있는 공식 지도

개발자들이 직접 써 놓은 전체 호출 계층도가 주석으로 들어 있습니다.
(아래는 원문을 그대로 옮긴 것입니다)

            PerformSolarCalculations           태양 위치·일사·음영

          CalcHeatBalanceInsideSurf            ★ 내표면 열평형

**읽는 방법**: 들여쓰기가 호출 깊이입니다.
알고리즘을 추적할 때는 위에서 아래로 따라가면서
관심 있는 단계의 함수명을 소스에서 검색하면 됩니다.

### 계산 순서의 핵심 논리

EnergyPlus는 **"예측(Predict) → 설비 시뮬레이션 → 보정(Correct)"** 구조입니다.

1. **Predict**: "설정온도를 맞추려면 존에 몇 W가 필요한가?" 를 계산
   → `ZoneTempPredictorCorrector.cc` 의 `PredictSystemLoads()` (2913줄)
2. **SimHVAC**: 그 요구량을 실제 설비(코일·팬·보일러·칠러)가 얼마나 공급 가능한지 계산
3. **Correct**: 실제 공급량으로 존 공기 온도를 다시 확정

> **이것이 EnergyPlus의 가장 중요한 개념적 특징**입니다.
> 단순 정적 계산(ISO 13790 류, 국내 건축물에너지효율등급 평가 방식)과 달리
> **설비의 용량 부족·부분부하 효율 저하가 실내 온도에 되먹임**됩니다.
> ZEB 검토에서 "설비가 부하를 못 따라가는 시간(Unmet Hours)"을 볼 수 있는 이유입니다.

## 2-6. 알고리즘 검증 시 반드시 함께 볼 것 — 공식 계산식 문서

소스코드만 읽으면 "무엇을 계산하는지"는 알지만 "왜 그 식인지"는 모릅니다.
`doc/engineering-reference/` 에 **592개 파일**로 공식 계산식 문서 원본이 들어 있습니다.
(설치 폴더의 `Documentation\` 에 PDF로도 있음)

**권장 작업 순서**:
1. Engineering Reference에서 해당 모델의 **수식과 가정**을 먼저 읽기
2. 그 다음 소스에서 **실제 구현**을 확인 (문서와 구현이 어긋난 경우도 있음)
3. `testfiles/` 에서 해당 기능을 쓰는 예제를 찾아 **실행하며 수치 확인**

3단계가 중요합니다. 819개 예제 입력파일은
사실상 **각 기능의 공식 사용 예시 겸 검증 케이스**입니다.
새로운 객체를 쓸 때는 이 중에서 grep으로 사용 예를 찾는 것이 가장 빠릅니다.

```bash
grep -l "HVACTemplate:System:VRF" testfiles/*.idf
```
