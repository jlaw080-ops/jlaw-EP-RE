# 11. 기상데이터 관리 — 버전 고정과 갱신 감시

> 결론: **자동 업데이트하지 않습니다.** 대신 채택 버전을 고정하고, 상위 배포본의
> 변경을 자동으로 감시해 사람에게 알립니다.

---

## 11-1. 왜 자동 업데이트를 하지 않는가

채택한 데이터는 **ISO 15927-4:2005 기준기상연도(TRY)** 입니다.
기준년의 존재 목적은 **재현성**입니다.

| 자동 업데이트하면 | 결과 |
|---|---|
| 기상파일이 조용히 바뀐다 | 작년 검토 결과와 올해 결과를 **비교할 수 없다** |
| 진행 중 과업의 기상파일이 바뀐다 | 그 과업의 **VE 대안 비교가 무효**가 된다 |
| 오류가 나지 않는다 | **바뀐 사실을 모른 채** 결과를 제출하게 된다 |

ZEB 인증·에너지절약계획서 등에서 "어느 기상파일로 돌렸는지"는 **근거의 일부**입니다.

### 이 위험은 가정이 아닙니다

채택한 파일은 **2005~2014년 실측 데이터**인데, 상위 배포본의 파일 최종 수정일은
**2026-03-10** 입니다. 상위에서 파일을 재배포한 것입니다.
내용이 바뀌었는지는 알 수 없습니다 — **그래서 체크섬을 고정합니다.**

---

## 11-2. 채택한 데이터

| 항목 | 내용 |
|---|---|
| 데이터 | 한국 기준기상연도(TRY) |
| 원본 | **기상청(KMA) 실측 2005~2014** |
| 가공 | ISO 15927-4:2005 |
| 제작 | **Passive House Institute Korea** |
| 배포 | Climate.OneBuilding.org |
| 지점 | **22개** (기상청 대표 관측지점과 거의 일치) |
| 포함 파일 | 지점별 `.epw`(시뮬레이션) + `.ddy`(설계일) + `.stat`(기후통계) |

```
서울 인천 수원 대전 대구 부산 광주 제주 고산 강릉 원주
춘천 대관령 안동 포항 진주 전주 청주 추풍령 서산 목포 흑산도
```

### TMYx 를 쓰지 않은 이유 — 일사량이 23% 다릅니다

같은 사이트에 `TMYx` 가 95개 지점 있지만 채택하지 않았습니다.

| | TRY_PHIKO (채택) | TMYx 2011-2025 |
|---|---|---|
| 일사 출처 | **기상청 실측** | NOAA ISD + **ERA5 재해석(위성·모델)** |
| 서울 연간 전일사 | **1,238.7 kWh/m²** | 1,528.7 kWh/m² |
| 서울 건구온도 | −13.0 ~ 33.4℃ | −17.2 ~ 35.7℃ |

**전 지점에서 같은 방향으로 일관된 차이**가 나타납니다(TMYx 가 직달 높고 확산 낮음).
서울 기준 **23% 차이**는 PV 발전량과 ZEB 자립률 판정을 바꿉니다.

> 국내 인증·기준 대응에는 **기상청 실측 기반 TRY_PHIKO** 를 씁니다.
> TMYx 는 최근 기후 추세를 보는 **보조 자료**로만 쓰십시오. 두 데이터를 섞어
> 비교하면 안 됩니다.

## 11-3. 구성

```
weather/
├── manifest.json          ★ 채택 버전 고정 — sha256·상위 ETag·품질지표
└── archive/               ★ 고정 보관본 22개 zip (저장소에 커밋, 8.1MB)

scripts/weather/
├── _http.py               상위 서버 통신 공용 유틸 (429 재시도·상태 확인)
├── fetch.py               보관본/상위에서 가져와 sha256 대조
├── verify_epw.py          품질 검증 (8,760행 · 일사 결측 · 값 범위)
└── check_updates.py       상위 변경 감시 (파일은 바꾸지 않음)

.github/workflows/
└── weather-check.yml      월 1회 자동 감시 → 변경 시 Issue 생성
```

### `manifest.json` 에 무엇이 들어있나

지점마다 다음을 기록합니다.

```jsonc
{
  "station": "Seoul", "region_code": "SO", "wmo": "471080",
  "archive": "KOR_SO_Seoul.471080_TRY_PHIKO.zip",
  "source_url": "https://climate.onebuilding.org/...",
  "upstream": {                    // 상위 배포본 상태 — 변경 감시의 기준점
    "etag": "\"5c795-...\"",
    "last_modified": "Tue, 10 Mar 2026 20:09:14 GMT",
    "content_length": 378773
  },
  "sha256_zip": "...",             // 고정값 — 이것과 다르면 채택하지 않는다
  "sha256_epw": "...",
  "verification": {                // 고정 당시의 품질 지표
    "rows": 8760, "solar_missing": 0,
    "drybulb_c_min": -13.0, "drybulb_c_max": 33.4,
    "global_horiz_kwh_m2": 1238.7,
    "direct_normal_kwh_m2": 969.4,
    "diffuse_horiz_kwh_m2": 671.0
  }
}
```

`verification` 값이 있어서 **상위가 파일을 바꿨을 때 "얼마나 달라졌는지"를
숫자로 비교**할 수 있습니다.

## 11-4. 쓰는 방법

### 기상파일 꺼내기

```bash
python3 scripts/weather/fetch.py
```

`weather/epw/` 에 22개 지점의 `.epw`·`.ddy`·`.stat` 가 풀립니다.
**네트워크가 필요 없습니다** — 저장소 보관본에서 복원하고 sha256 으로 대조합니다.
(보관본이 없거나 해시가 다를 때만 상위 서버를 씁니다.)

### 품질 검증

```bash
python3 scripts/weather/verify_epw.py weather/epw
```

### 상위 변경 확인 (손으로)

```bash
python3 scripts/weather/check_updates.py
```

종료코드 — `0` 변경 없음 / `10` 변경 감지 / `1` 점검 실패(판정 불가)

## 11-5. 자동 감시

`.github/workflows/weather-check.yml` 이 **매월 3일 11:17(한국시간)** 에 돕니다.

```
① 22개 지점의 ETag·Last-Modified·크기를 상위와 비교
② TMYx 에 새 기간판(예: 2013-2027)이 생겼는지 확인
③ 변경이 있으면 Issue 생성 (라벨 weather-data)
   같은 제목의 열린 Issue 가 있으면 중복 생성하지 않는다
④ 파일은 절대 자동 교체하지 않는다
```

손으로 돌리려면 저장소 **Actions 탭 → 기상파일 갱신 감시 → Run workflow**.

### TMYx 기간판 주기

```
2004-2018 → 2007-2021 → 2009-2023 → 2011-2025
```

약 2년 간격입니다. 다음은 2013-2027쯤으로 예상됩니다.

## 11-6. 변경이 감지되면 — 처리 순서

Issue 가 열리면 다음 순서로 **사람이 판단**합니다.

```
1. python3 scripts/weather/fetch.py
   → 체크섬 불일치가 나는 지점을 확인

2. python3 scripts/weather/verify_epw.py weather/epw
   → 8,760행·일사 결측·값 범위가 여전히 정상인지

3. manifest.json 의 verification 값과 새 값을 비교
   → 연간 전일사·건구온도가 얼마나 달라졌는지 크기를 파악

4. 채택 여부 결정
   → 채택하면 manifest.json 을 갱신하고 커밋 메시지에 '왜 바꿨는지' 기록
   → git 이력이 그대로 기상파일 채택 이력이 된다
```

> **진행 중인 과업이 있으면 그 과업이 끝난 뒤에 갱신하십시오.** 중간에 바꾸면
> 이미 돌린 케이스와 앞으로 돌릴 케이스를 비교할 수 없습니다.

## 11-7. 설계 판단 기록

### 보관 방식 — 저장소 커밋을 택한 이유

| 방안 | 판단 |
|---|---|
| **저장소에 zip 커밋 (채택)** | 8.1MB. 네트워크·상위 서버 상태와 무관하게 동작. 완전 자립 |
| GitHub Release 자산 | git 이력을 깨끗하게 두지만, 릴리스 생성이 별도 수작업 |
| 체크섬만 기록 | 상위가 파일을 교체·삭제하면 **원본을 잃는다** |

처음에는 Release 자산을 권했으나, 저장소 커밋으로 바꿨습니다. 이유는
**기상파일이 "한 번 정하면 수년간 바뀌지 않는 기준 자산"** 이고, 8.1MB 는
문서 저장소에 감당 가능한 크기이며, 무엇보다 **보관본이 저장소 안에 있으면
네트워크 없이도 누구나 같은 결과를 재현**할 수 있기 때문입니다.

Release 로 옮기고 싶으면 `manifest.json` 의 `source_url` 만 릴리스 자산 주소로
바꾸면 됩니다. 스크립트는 그대로 동작합니다.

### 상위 서버 429 대응 — 실측으로 발견한 문제

개발 중 `fetch.py` 가 **"상위 배포본이 바뀌었다"는 거짓 경보**를 냈습니다.
원인은 상위 서버의 **HTTP 429 Too Many Requests** 였습니다.

```
curl -o 는 오류 본문도 파일에 쓴다
  → 227바이트 429 HTML 이 zip 으로 저장된다
  → 그 해시가 "체크섬 불일치" 로 보고된다
  → 일시적 실패가 '상위가 바뀌었다' 는 신호로 둔갑한다
```

이 체계에서 **가장 중요한 신호가 오염되는** 문제였으므로,
모든 요청을 `_http.py` 로 모아 다음을 보장하게 했습니다.

- HTTP 상태를 확인하고, 200 이 아니면 실패로 처리
- 429·5xx 는 백오프 재시도 (3초 → 6초 → 12초)
- 요청 사이 1초 간격
- **실패한 응답을 결과 파일로 남기지 않음** (임시파일에 받아 200 일 때만 이동)
- 받기 실패와 체크섬 불일치를 **구분해 보고**

### 검증 기준

`rows = 8760` 이고 `solar_missing = 0` 이어야 채택합니다.

일사량 결측이 특히 중요합니다. EnergyPlus 는 **일사 결측을 0 으로 대체하고
오류를 내지 않습니다** ([`04-자동화.md`](04-자동화.md) 참조).
해가 없는 것으로 계산되어 냉방부하가 과소평가되고 PV 발전량은 0 이 되는데,
숫자는 멀쩡히 나오므로 모르고 지나칠 수 있습니다.

## 11-8. 범위 밖 — 기상청 원시 관측(ASOS) 직접 수집

실측연도(AMY) 해석이나 준공 후 실측 검증(M&V)에는 기상청 원시 관측이 필요합니다.
이것은 **기준년과 용도가 다른 별건**입니다.

| 경로 | 비고 |
|---|---|
| `apihub.kma.go.kr` | API 키 필요 |
| `data.kma.go.kr` (기상자료개방포털) | API 키 필요 |
| `data.go.kr` (공공데이터포털) | API 키 필요 |

**선행 과제**: 기상청 ASOS 는 보통 **전일사량만** 제공하는데, EnergyPlus 는
**직달법선 + 확산수평**으로 계산합니다. WeatherConverter 에는 전일사 단독에서
이를 분리하는 경로가 없으므로, 외부 분리 모델(Erbs·Reindl·Perez 등)을
먼저 적용해야 합니다.
