# 03. 입력파일 구조 해부 — IDD와 epJSON

> 목표: 입력파일(IDF)을 **프로그램으로 자동 생성·수정·검증**하는 도구를 만들기 위한 기반 분석

## 3-1. 핵심 개념 — IDD는 "입력 규칙서"다

EnergyPlus 입력 체계는 2개 파일의 쌍으로 돌아갑니다.

| 파일 | 역할 | 비유 |
|---|---|---|
| `Energy+.idd` | **규칙서**. 어떤 객체가 존재하고 각 필드가 무엇인지 정의 | 엑셀 양식의 서식 정의 |
| `내모델.idf` | **실제 데이터**. 규칙서에 맞춰 값을 채운 것 | 양식에 기입한 내용 |

`Energy+.idd`는 설치 폴더 루트에 있고, **텍스트 파일**입니다.
v26.2.0 기준 **877개 객체 / 11.1만 줄 / 4.6MB**.

**이 파일 하나가 "EnergyPlus가 할 수 있는 모든 것의 완전한 목록"입니다.**
입력 자동 생성 도구를 만드는 작업은 결국 이 파일을 기계가 읽게 만드는 일입니다.

## 3-2. IDD 문법 해부 — 실제 예시로

소스 `idd/Energy+.idd.in` 의 `Zone` 객체 정의 (실물 발췌):

```
Zone,
       \memo Defines a thermal zone of the building. Every zone contains one or more Spaces.
       \format vertices
  A1 , \field Name
       \note Name of the Zone.
       \required-field
       \type alpha
       \reference ZoneNames
  N1 , \field Direction of Relative North
       \units deg
       \type real
       \default 0
  N2 , \field X Origin
       \units m
       \type real
       \default 0
```

### 문법 규칙

| 기호 | 의미 |
|---|---|
| `Zone,` | 객체(클래스) 이름. 줄 맨 앞에서 시작하고 쉼표로 끝남 |
| `A1`, `A2`, … | **A = Alpha 필드** (문자열). 순번이 입력 순서 |
| `N1`, `N2`, … | **N = Numeric 필드** (숫자). 순번이 입력 순서 |
| `\field` | 필드의 사람이 읽는 이름 |
| `\type` | 자료형: `alpha` / `real` / `integer` / `choice` / `object-list` / `node` |
| `\units` | 단위 (**EnergyPlus 내부는 전부 SI 단위**) |
| `\default` | 생략 시 기본값 |
| `\required-field` | 필수 입력 |
| `\minimum` / `\maximum` | 값 범위 (`\minimum>` 는 초과, `\minimum` 는 이상) |
| `\reference` | 이 필드 값을 다른 객체가 참조할 수 있도록 등록하는 **이름 그룹** |
| `\object-list` | 반대로, 특정 `\reference` 그룹에서 값을 골라야 함 |
| `\key` | `choice` 타입에서 허용되는 선택지 |
| `\memo` / `\note` | 설명문 |
| `\format` | 작성 형식 힌트 (`vertices` = 좌표를 보기좋게 배열) |
| `\extensible:N` | 마지막 N개 필드가 **반복 가능**(스케줄, 다각형 좌표 등) |
| `\min-fields` | 최소 입력 필드 수 |

### 자동 검증 도구를 만들 때 핵심이 되는 것: `\reference` ↔ `\object-list`

위 예시에서 `Zone` 의 Name 필드는 `\reference ZoneNames` 로 등록됩니다.
그러면 다른 객체(예: `People`)의 Zone 이름 필드는 `\object-list ZoneNames` 로 선언되어
**Zone으로 등록된 이름만 받아들입니다.**

이 쌍이 **IDF 파일 전체의 참조 정합성(referential integrity)** 을 규정합니다.
입력 자동 생성 도구에서 가장 흔한 오류가
"존재하지 않는 Zone/Schedule/Node 이름 참조"인데,
`\reference`/`\object-list` 쌍만 구현하면 **실행 전에 미리 잡아낼 수 있습니다.**

> 참고: `Zone`의 Name은 `ZoneNames`, `OutFaceEnvNames`, `ZoneAndZoneListNames`,
> `ZoneAndZoneListAndSpaceAndSpaceListNames`, `AirflowNetworkNodeAndZoneNames`
> 등 **5개 그룹에 동시 등록**됩니다. 참조 그룹은 다대다 관계입니다.

## 3-3. epJSON — 자동화에는 이쪽이 정답

EnergyPlus는 IDF 외에 **epJSON**(JSON 형식) 입력을 공식 지원합니다.
설치 폴더 루트의 `Energy+.schema.epJSON` 이 그 스키마(JSON Schema 형식)입니다.

### IDF vs epJSON 비교

```idf
Zone,
  Zone1,      !- Name
  0.0,        !- Direction of Relative North {deg}
  0.0,        !- X Origin {m}
  0.0,        !- Y Origin {m}
  0.0;        !- Z Origin {m}
```

```json
{
  "Zone": {
    "Zone1": {
      "direction_of_relative_north": 0.0,
      "x_origin": 0.0,
      "y_origin": 0.0,
      "z_origin": 0.0
    }
  }
}
```

### 자동화 관점에서 epJSON이 압도적으로 유리한 이유

| 항목 | IDF | epJSON |
|---|---|---|
| 필드 식별 | **순서(위치)로 식별** → 중간 필드 누락 시 전체 밀림 | **이름(key)으로 식별** → 안전 |
| 파싱 | 전용 파서 필요 (주석 `!-`, 쉼표/세미콜론 규칙) | 표준 JSON 라이브러리로 즉시 가능 |
| 검증 | 별도 구현 필요 | **JSON Schema 표준 검증기 사용 가능** |
| 부분 수정 | 텍스트 치환 → 위험 | 키 접근 → 안전 |
| 웹/DB 연동 | 변환 필요 | 그대로 저장·전송 가능 |

> **결론 및 권고**: 입력 자동 생성·파라메트릭 VE 검토 도구는
> **epJSON을 1차 포맷으로 채택**하는 것이 맞습니다.
> IDF는 사람이 읽고 기존 모델을 받아들이는 입출력 호환 포맷으로만 쓰십시오.

### 포맷 변환 방법

EnergyPlus 자체가 변환기를 내장하고 있습니다. (근거: `CommandLineInterface.cc` 155·157줄)

```bash
energyplus --convert-only in.idf
```

```bash
energyplus -c -w weather.epw in.idf
```

- `--convert-only` : 변환만 하고 시뮬레이션은 하지 않음
- `-c, --convert` : 시뮬레이션과 함께 IDF↔epJSON 변환 결과도 출력
- 별도 독립 도구도 존재: `src/ConvertInputFormat/` (설치 폴더 `PreProcess\` 에 실행파일)

## 3-4. 스키마를 기계가 읽게 만드는 공식 코드 — 바퀴를 다시 발명하지 말 것

**중요한 발견**: IDD를 파싱하는 코드를 직접 쓸 필요가 없습니다.
NREL이 파이썬으로 이미 작성해 두었고, 소스에 포함되어 있습니다.

| 파일 | 역할 | 크기 |
|---|---|---|
| `idd/schema/idd_parser.py` | **IDD 텍스트 → 파이썬 자료구조 파서** | 35KB |
| `idd/schema/generate_epJSON_schema.py` | 파싱 결과 → JSON Schema 생성 | 5.4KB |
| `idd/schema/modify_schema.py` | 스키마 후처리(예외 규칙 적용) | 17KB |
| `idd/schema/test_idd_parser.py` | 파서 테스트 (사용법 예시로 유용) | 8KB |

**즉 입력 자동 생성 도구의 1단계는 이렇게 됩니다**:

1. `idd_parser.py` 를 가져와 `Energy+.idd` 를 파싱
2. 877개 객체의 필드 정의·타입·단위·기본값·참조관계를 구조화된 데이터로 확보
3. 이것을 DB나 TypeScript 타입으로 내보내 **입력 UI를 자동 생성**

3번이 핵심 아이디어입니다. 877개 객체의 입력 양식을 손으로 만들 수는 없지만,
**스키마에서 자동 생성하면 가능**하고 버전 업 시에도 재생성만 하면 됩니다.

> 라이선스상 이 파이썬 코드를 가져다 쓰는 것은 허용됩니다(BSD 계열).
> 단 저작권 표시를 유지하고, [README의 제4항 주의사항](../README.md)을 지키십시오.

## 3-5. 버전 호환성 — 자동화 도구의 최대 함정

EnergyPlus는 버전마다 **입력 객체가 바뀝니다**(필드 추가/삭제/순서 변경).
26.2.0용 IDF는 27.1.0에서 그대로 돌아가지 않습니다.

소스에 공식 변환기가 있습니다.

| 경로 | 역할 |
|---|---|
| `src/Transition/` | 버전 간 IDF 자동 변환 엔진 |
| `src/IDFVersionUpdater/` | 그 GUI 래퍼 (설치 폴더 `PreProcess\IDFVersionUpdater\`) |
| `idd/versions/` | 과거 버전 IDD 보관 |

**자동화 도구 설계 시 반드시 할 일**:
입력파일의 `Version` 객체 값을 읽어 엔진 버전과 일치하는지 **먼저 확인**하고,
불일치 시 변환기를 거치게 하십시오. 이 체크를 빼면 원인 불명의 오류로 시간을 잃습니다.

```bash
grep -i -A2 "^Version," 내모델.idf
```
