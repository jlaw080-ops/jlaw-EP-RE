# 05. 웹서비스 구축 — Vercel 환경에서의 현실적 아키텍처

> 사용자님의 기존 배포 프로세스(GitHub → Vercel)를 전제로 검토했습니다.

## 5-1. 결론 먼저 — Vercel 함수에 EnergyPlus를 넣는 것은 안 됩니다

EnergyPlus를 Vercel의 일반 서버리스 함수(Serverless Function) 안에서
직접 실행하는 구조는 **구조적으로 맞지 않습니다.** 이유는 세 가지입니다.

### (1) 실행 시간

[`02-계산엔진.md`](02-계산엔진.md)에서 확인했듯 연간 시뮬레이션 1회는
`365 × 24 × 6 ≈ 52,560` 타임스텝의 열평형 계산 + Warmup 반복입니다.
모델 규모에 따라 **수십 초에서 수 분**이 걸립니다.

Vercel 함수는 `maxDuration` 을 설정할 수 있지만(`vercel.json` 의 `functions` 항목),
요금제별 상한이 있고 **사용자를 수 분간 HTTP 응답 대기시키는 구조 자체가 부적절**합니다.

### (2) 번들 용량

EnergyPlus는 실행파일 외에 `Energy+.idd`(4.6MB), 스키마, 데이터셋, 파이썬 런타임까지
함께 있어야 동작합니다. 설치 폴더 전체가 **수백 MB 규모**입니다.

사용자님 PC에서 실제 크기를 확인해 보십시오.

```powershell
"{0:N0} MB" -f ((Get-ChildItem "C:\EnergyPlusV26-2-0" -Recurse -File | Measure-Object Length -Sum).Sum / 1MB)
```

Vercel Python 런타임 문서는 번들 **500MB 상한**을 명시하고 있어
들어갈 수 있을지조차 아슬아슬하고, 들어가도 콜드스타트가 심각해집니다.

### (3) 단일 코어 + 상태 유지

EnergyPlus는 1코어를 100% 점유하며 순차 계산하고,
중간 결과를 **파일시스템에 씁니다**(33종 출력파일).
서버리스 함수의 읽기전용/임시 파일시스템 모델과 잘 맞지 않습니다.

## 5-2. 그렇다면 어떻게? — 역할 분리가 정답

**Vercel을 버리는 것이 아니라, Vercel이 잘하는 일만 시키는 것**입니다.

```
┌─────────────────────────────────────────────┐
│  Vercel  (프론트엔드 + API 게이트웨이)        │  ← 사용자님의 기존 프로세스 유지
│  · 입력 UI (877개 객체 스키마 기반 자동생성)   │
│  · 케이스 관리 / 결과 조회 / 그래프            │
│  · 작업 큐에 "계산 요청" 등록                  │
└────────────────┬────────────────────────────┘
                 │ (작업 요청 / 상태 폴링)
┌────────────────▼────────────────────────────┐
│  계산 실행 계층  (아래 3가지 중 선택)          │
│  · EnergyPlus 바이너리 실행                   │
│  · 수 분 단위 장시간 실행 허용                 │
└────────────────┬────────────────────────────┘
                 │ (결과 .sql / 요약 JSON)
┌────────────────▼────────────────────────────┐
│  저장 계층 (Supabase / Postgres + 파일저장)   │
│  · 모델 입력(epJSON) / 결과 요약 / 원본 파일   │
└─────────────────────────────────────────────┘
```

## 5-3. 계산 실행 계층 — 3가지 선택지

### 선택지 A. Vercel Sandbox ★ 사용자님 환경에 가장 잘 맞음

Vercel에는 일반 함수와 별도로 **Sandbox** 가 있습니다.
이것은 함수가 아니라 **실제 리눅스 VM**이며, 임의의 바이너리를 실행할 수 있습니다.

공식 문서에서 확인한 특성:

| 항목 | 내용 |
|---|---|
| 실행 환경 | 리눅스 VM (`createUser` 로 리눅스 사용자 생성 가능 수준의 완전한 환경) |
| vCPU | 설정 가능 (`sandbox config vcpus my-sandbox 4`) |
| 세션 시간 | 설정 가능 (`sandbox config timeout my-sandbox 30m`), 실행 중 연장도 가능 (`extend_execution_time_limit`) |
| 영구 저장 | Drive 마운트 지원 (기본 1TiB, Hobby 요금제는 1GiB) |
| 동시 실행 | 요금제별 제한 (Hobby는 동시 10개, 세션 최대 45분) |
| SDK | TypeScript / Python 모두 제공 |

**이것이 중요한 이유**: Drive 기능으로 **EnergyPlus 설치본을 한 번 올려두고 재사용**할 수 있습니다.
매 요청마다 수백 MB를 내려받지 않아도 됩니다.
또한 Vercel 생태계 안에 있으므로 사용자님의 기존 배포 프로세스가 그대로 유지됩니다.

> 주의: 요금제별 정확한 상한과 과금(실행 시간·vCPU·네트워크)은
> 사용자님 계정의 요금제에 따라 다릅니다. **실제 도입 전 요금 계산이 필요합니다.**
> 연간 시뮬레이션은 CPU를 길게 점유하므로 과금에 직접 영향을 줍니다.

### 선택지 B. 컨테이너 기반 서비스 (Fly.io / Railway / Cloud Run / Fargate)

Docker 이미지에 EnergyPlus를 넣어 배포하는 전통적 방식입니다.

- 장점: 완전한 제어, 장시간 실행 자유, EnergyPlus 공식 Docker 이미지 활용 가능
- 단점: Vercel 외부 인프라가 추가됨 (관리 대상 2곳)
- 추천: 동시 사용자가 많거나, 계산을 상시 돌릴 때

### 선택지 C. 사용자 PC에서 계산, 웹은 관리만 ★ 1단계로 추천

웹앱은 **입력 생성과 결과 조회만** 담당하고,
실제 계산은 사용자님 PC(또는 사내 워크스테이션)에서 돌립니다.

```
Vercel 웹앱  ──(epJSON 케이스 다운로드)──▶  로컬 실행 스크립트
      ▲                                           │
      └────────(결과 요약 JSON 업로드)─────────────┘
```

- 장점: **비용 0**, 계산 시간 제약 없음, 기존 PC 성능 활용(병렬 실행)
- 단점: PC가 켜져 있어야 함, 외부 고객에게 서비스 불가
- 추천: **프로젝트 초기 단계 / 사내 도구**

> **권고**: C로 시작해 핵심 로직(케이스 생성·실행·집계)을 먼저 완성하십시오.
> 그 로직은 A나 B로 옮길 때 거의 그대로 재사용됩니다.
> 반대로 인프라부터 고르면, 정작 만들 것이 무엇인지 모르는 상태에서 비용이 발생합니다.

## 5-4. 비동기 처리 — 필수 설계 요소

어떤 선택지든 **"요청 → 즉시 응답"이 불가능**하므로 비동기 구조가 필수입니다.

```
1. POST /api/simulations     → 작업 등록, job_id 즉시 반환 (계산 시작 안 기다림)
2. 계산 실행 계층이 작업 수행 (수십 초 ~ 수 분)
3. GET  /api/simulations/:id → 상태 조회 (queued / running / done / failed)
4. 완료 후 결과 조회
```

진행률 표시는 Python API의 콜백으로 구현할 수 있습니다.
([`04-자동화.md`](04-자동화.md) 4-5절의 `callback_progress` / `callback_message`)
수 분간 아무 표시도 없는 화면은 사용자가 고장으로 오인합니다.

## 5-5. 저장 설계 — 무엇을 DB에 넣을 것인가

| 데이터 | 저장 방식 | 이유 |
|---|---|---|
| 모델 입력 (epJSON) | **DB의 JSON 컬럼** | JSON 그대로 저장·질의 가능 ([`03-입력스키마.md`](03-입력스키마.md)) |
| 결과 요약 (연간 에너지, 자립률 등) | **DB 테이블** | 케이스 간 비교·정렬·그래프의 대상 |
| `eplusout.sql` 원본 | **파일 저장소** (Supabase Storage / Blob) | 수 MB~수십 MB. DB에 넣을 것 아님 |
| `.err` / `.end` | **텍스트 컬럼** | 오류 원인 추적에 필요. 작음 |
| 33종 기타 출력 | 보관 선택 | 대부분 재현 가능하므로 버려도 됨 |

> epJSON을 그대로 DB에 넣을 수 있다는 점이 **IDF 대신 epJSON을 쓰는 가장 실용적인 이유**입니다.
> IDF는 텍스트 덩어리라 DB에서 질의할 수 없지만,
> epJSON은 "창호 U값이 1.0 이하인 케이스" 같은 질의가 DB 레벨에서 가능합니다.

## 5-7. 단계별 로드맵 제안

| 단계 | 목표 | 산출물 | 선택지 |
|---|---|---|---|
| **1** | 로컬 자동 실행 확립 | 케이스 생성 + 병렬 실행 + 결과 집계 스크립트 | C |
| **2** | 스키마 기반 입력 생성 | `idd_parser.py` 활용한 epJSON 생성기 + 검증기 | C |
| **3** | 웹 UI (조회 전용) | Vercel 앱 + DB. 결과를 보고 비교하는 화면 | C |
| **4** | 웹에서 계산 요청 | 비동기 작업 큐 + 실행 계층 연결 | A 또는 B |
| **5** | 외부 서비스화 | 인증·과금·동시성·요금 최적화 | A 또는 B |

1~2단계가 전체 가치의 대부분을 만듭니다.
**파라메트릭 VE 검토 자동화 자체가 목적이라면 2단계에서 멈춰도 충분**하고,
웹화는 여러 사람이 함께 쓸 필요가 생겼을 때 진행하면 됩니다.
