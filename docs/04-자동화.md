# 04. 자동 실행과 결과 추출 — 파라메트릭 VE 검토 자동화

> 목표: 수십~수백 케이스를 자동으로 돌리고 결과를 비교하는 파이프라인 구축

## 4-1. 자동화 방식 3가지 비교 — 먼저 고르고 들어가야 합니다

| 방식 | 설명 | 장점 | 단점 | 추천 용도 |
|---|---|---|---|---|
| **A. CLI 호출** | `energyplus.exe`를 명령줄로 반복 실행 | 가장 단순, 안정적, 병렬화 쉬움 | 시뮬레이션 중간 개입 불가 | ★ **파라메트릭 VE 검토** |
| **B. Python API** | 엔진을 라이브러리로 불러 제어 | 시뮬레이션 **중간에 값 읽고 쓰기** 가능 | 복잡도 높음 | 제어로직 개발, 최적화 |
| **C. Python Plugin** | IDF 안에 파이썬 코드를 박아 실행 | 입력파일 하나로 완결 | 디버깅 어려움 | 커스텀 제어·설비 모델 |

**권고**: 파라메트릭 VE 검토가 목적이면 **A(CLI)로 시작**하십시오.
B는 "최적 설정온도를 실시간으로 바꿔가며 찾는다" 같은 경우에만 필요합니다.

## 4-2. 방식 A — CLI 옵션 전체 (실측)

근거: `src/EnergyPlus/CommandLineInterface.cc` 127~236줄의 실제 옵션 정의부

| 옵션 | 긴 형태 | 기능 |
|---|---|---|
| `-w` | `--weather` | 기상파일 경로 (기본값: 현재 폴더의 `in.epw`) |
| `-d` | `--output-directory` | **출력 폴더 지정** (기본값: 현재 폴더) |
| `-p` | `--output-prefix` | **출력 파일명 접두어** (기본값: `eplus`) |
| `-s` | `--output-suffix` | 출력 파일명 접미 형식 |
| `-a` | `--annual` | 연간 시뮬레이션 강제 |
| `-D` | `--design-day` | **설계일만 계산** (빠른 검증용, `-a`와 배타) |
| `-r` | `--readvars` | 시뮬레이션 후 ReadVarsESO 실행 → **CSV 자동 생성** |
| `-c` | `--convert` | IDF↔epJSON 변환 결과도 출력 |
| | `--convert-only` | 변환만 수행 |
| `-m` | `--epmacro` | EPMacro 전처리 실행 |
| `-x` | `--expandobjects` | **HVACTemplate 확장 전처리 실행** |
| `-j` | `--jobs` | 병렬 작업 수 |
| | (위치 인자) | 입력파일 (기본값: 현재 폴더의 `in.idf`) |

> 하위 명령도 있습니다: `energyplus epLaunch`, `energyplus idfUpdater`,
> `energyplus gheDesigner` (지중열교환기 설계 도구) 등.

### 파라메트릭 자동 실행의 핵심 조합

```bash
energyplus -w weather.epw -d ./out/case_01 -p case_01 -x -r -a model_01.idf
```

- `-d` 와 `-p` 를 케이스마다 다르게 주는 것이 **핵심**입니다.
  이 두 옵션이 없으면 모든 케이스가 같은 파일명으로 서로를 덮어씁니다.
- `-x` 는 `HVACTemplate:` 객체를 쓴 모델이면 **반드시** 필요합니다.
- `-r` 을 주면 `.eso` 를 CSV로 바로 바꿔주므로 후처리가 쉬워집니다.

### 병렬 실행 — 가장 큰 성능 이득

연간 시뮬레이션 **한 건**은 CPU 1코어만 씁니다
([`02-계산엔진.md`](02-계산엔진.md)의 시간 루프 구조상 본질적으로 순차 계산).
따라서 가속 방법은 **케이스 단위 병렬**입니다.

8코어 PC에서 동시 6~7개를 돌리면 거의 선형으로 빨라집니다.
(1코어는 OS 여유로 남겨두는 것이 안정적)

### ★ 케이스 단위 병렬에는 두 가지 방식이 있습니다

**근거**: 공식 문서 `InputOutputReference` §1.4 "Using EnergyPlus as a Library" (p38)

| 방식 | 설명 | 적합한 곳 |
|---|---|---|
| **프로세스 병렬** | `energyplus.exe`를 N개 동시 실행 | 로컬 배치 스크립트. 가장 단순하고 안정적 |
| **스레드 병렬** | 한 프로세스 안에서 state 인스턴스를 여러 개 만들어 스레드로 실행 | 웹서비스 백엔드. 프로세스 생성 오버헤드·메모리 중복 없음 |

스레드 병렬이 가능한 이유는 **EnergyPlus 9.5부터 스레드 안전(thread-safe)** 이기 때문입니다.
공식 문서의 API 연혁:

| 버전 | 변화 |
|---|---|
| 9.3 | 현대적 API 최초 도입 |
| 9.4 | 시뮬레이션 상태 `reset` 신뢰성 확보 |
| **9.5** | **전역·정적 변수 17,000개를 state 객체로 리팩터링 → 스레드 간 간섭 없음** |
| 9.6 | API 클라이언트가 Python Plugin 포함 입력파일도 실행 가능 |

> 이것이 [`02-계산엔진.md`](02-계산엔진.md) 2-1절에서 본
> "`main.cc`가 10줄뿐이고 엔진이 `api/`에 라이브러리로 분리되어 있다"의 목적입니다.
> 소스 구조에서 추측했던 것을 공식 문서가 확인해 줍니다.
>
> **단, 1단계에서는 프로세스 병렬로 시작하십시오.** 더 단순하고, 한 케이스가
> 죽어도 나머지에 영향이 없습니다. 스레드 병렬은 웹서비스 단계에서 검토할 사항입니다.

### ★ SQLite 출력을 반드시 쓰십시오

`.sql` 하나에 **시계열·요약표·사이징·오류가 전부** 들어갑니다.
CSV를 여러 개 파싱하는 대신 SQL 한 번으로 끝납니다.

활성화 방법 — IDF에 이 객체를 넣습니다.

```idf
Output:SQLite,
  SimpleAndTabular;   !- Option Type
```

`SimpleAndTabular` 로 하면 요약표까지 DB에 들어갑니다.
그러면 "케이스 100개의 연간 1차에너지소요량"을 뽑는 작업이
**100개 폴더의 HTML을 파싱하는 일**에서 **SQL 쿼리 100번**으로 바뀝니다.

관련 소스는 `src/EnergyPlus/SQLiteProcedures.cc` 이고,
공식 스키마 문서는 `OutputDetailsAndExamples` §2.20 (p151~172) 입니다.

### SQLite 테이블 구조 (33개)

```
ReportDataDictionary ──┐
                       ├─→ ReportData ──→ Time          시계열 값
                       └─→ ReportExtendedData           월 최대/최소값과 발생 시점

TabularDataWithStrings                                  요약표 전체 (뷰)
TabularData / Strings / StringTypes                     위 뷰의 원본 테이블
Errors                                                  오류·경고 메시지
Zones / ZoneLists / ZoneGroups / ZoneInfoLists          존 정보
Surfaces / Constructions / ConstructionLayers / Materials   외피 구성
ZoneSizes / SystemSizes / ComponentSizes                사이징 결과
Nominal{People,Lighting,ElectricEquipment,GasEquipment,
        OtherEquipment,BaseboardHeaters,HotWaterEquipment,
        SteamEquipment,Infiltration,Ventilation}        입력 요약
Schedules / RoomAirModels / EnvironmentPeriods / Simulations
```

핵심 테이블 3개만 알면 됩니다.

| 테이블 | 용도 |
|---|---|
| **`TabularDataWithStrings`** | 요약표(연간 에너지, 자립률, Unmet Hours 등) — **VE 비교의 주 대상** |
| **`Errors`** | 오류·경고 — `.err` 파싱이 대부분 불필요해짐 |
| `ReportData` + `ReportDataDictionary` + `Time` | 시계열 상세 (시간별 부하 분석 등) |

> `TabularDataWithStrings` 는 실제 테이블이 아니라 **뷰(view)** 이고,
> `Output:SQLite` 를 `SimpleAndTabular` 로 지정했을 때만 생성됩니다.
> `Simple` 로 두면 요약표가 DB에 들어오지 않습니다.

### 질의 예 (공식 문서 수록)

```sql
SELECT * FROM TabularDataWithStrings
WHERE ReportName = 'AnnualBuildingUtilityPerformanceSummary'
  AND TableName  = 'Site and Source Energy';
```

`TabularDataWithStrings` 의 열 구조는
`ReportName` / `ReportForString` / `TableName` / `RowName` / `ColumnName` / `Value` / `Units`
입니다. 즉 **HTML 요약표의 모든 칸이 한 행씩 들어있는 형태**이므로,
원하는 숫자를 `RowName`·`ColumnName` 으로 정확히 지정해 꺼낼 수 있습니다.

```sql
-- 오류·경고 확인
SELECT * FROM Errors;
```

## 4-4. 성공/실패 자동 판정 — 파이프라인의 필수 요소

케이스 100개를 돌리면 반드시 몇 개는 실패합니다.
**자동 판정 로직 없이는 쓸 수 없는 결과를 모르고 비교하게 됩니다.**

### ★ 먼저 알아야 할 함정 — `.sql` 만 믿으면 안 됩니다

공식 문서 `OutputDetailsAndExamples` §2.20.4.8 (Errors Table) 의 경고입니다.

> *"errors experienced while processing input cause EnergyPlus to exit before the
> SQLite output database has been initialized. This is because the Output:SQLite object
> must be parsed from the input to request the database. Therefore, failures in input
> processing are indicated by the **absence of a SQLite output file**."*

**입력 처리 단계에서 실패하면 `.sql` 파일이 아예 생성되지 않습니다.**
`Output:SQLite` 객체 자체를 입력에서 읽어야 DB를 만들기 때문입니다.

그래서 "DB의 `Errors` 테이블을 열어 오류를 확인한다"는 로직만 두면
**가장 흔한 실패 유형(입력 오류)을 전혀 감지하지 못합니다.**
케이스가 조용히 사라지고, 집계에서는 그냥 누락됩니다.

> **`.sql` 파일의 부재 자체가 "입력 오류" 신호입니다.** 이 경우 원인은
> `.err` 와 `.audit` 에서만 찾을 수 있습니다.

### 권장 판정 순서

0. **`.sql` 파일 존재 확인** — 없으면 입력 오류 확정 → `.err` 로 원인 추적, 실패 처리
1. **`eplusout.end` 확인** — 이 파일은 딱 한 줄이고, 문구가 소스에 고정되어 있습니다.
   (근거: `src/EnergyPlus/*.cc` 실측 문자열)

   | 결과 | `.end` 내용 |
   |---|---|
   | 성공 | `EnergyPlus Completed Successfully-- N Warning; N Severe Errors; Elapsed Time=...` |
   | 치명적 오류 | `EnergyPlus Terminated--Fatal Error Detected. N Warning; N Severe Errors; Elapsed Time=...` |
   | 일반 오류 | `EnergyPlus Terminated--Error(s) Detected.` |

   즉 `.end` 한 줄만 읽으면 **성공 여부 + 경고 수 + Severe 오류 수 + 소요시간**을
   한 번에 얻습니다. 자동 판정의 1차 관문으로 이보다 효율적인 것은 없습니다.
2. **오류·경고 확인** — DB의 `Errors` 테이블 (또는 `.err` 에서 `** Severe **`, `** Fatal **`)
3. **Warmup 수렴 경고 확인** — Warmup 관련 경고 검색
   ([`02-계산엔진.md`](02-계산엔진.md) 2-3절 참조. ZEB 모델에서 특히 중요)
4. **Unmet Hours 확인** — 설정온도 미달 시간이 과도하면 설비 용량 부족

   ```sql
   SELECT RowName, Value, Units FROM TabularDataWithStrings
   WHERE ReportName = 'AnnualBuildingUtilityPerformanceSummary'
     AND TableName  = 'Comfort and Setpoint Not Met Summary';
   ```

   반환되는 행: `Time Set Point Not Met During Occupied Heating`,
   `Time Set Point Not Met During Occupied Cooling`,
   `Time Not Comfortable Based on Simple ASHRAE 55-2004` (단위: 시간)

> 3번과 4번은 "오류는 없지만 결과를 믿을 수 없는" 경우를 잡아냅니다.
> **VE 검토에서 가장 위험한 케이스가 바로 이것**입니다.
> 숫자가 나왔으니 비교해버리기 쉽지만, 전제가 깨진 결과입니다.

## 4-5. 방식 B — Python API 구조 (고급)

엔진이 `api/` 폴더에 라이브러리로 분리되어 있기 때문에
**파이썬에서 엔진을 직접 제어**할 수 있습니다.

### 구성

| 파일 | 역할 |
|---|---|
| `src/EnergyPlus/api/api.py` | 최상위 진입점 `EnergyPlusAPI` 클래스 |
| `src/EnergyPlus/api/runtime.py` | 실행 제어 + **콜백 등록** |
| `src/EnergyPlus/api/datatransfer.py` | **시뮬레이션 중 값 읽기/쓰기** |
| `src/EnergyPlus/api/func.py` | 물성 계산 등 독립 함수 |
| `src/EnergyPlus/api/autosizing.py` | 사이징 계산 단독 호출 |
| `src/EnergyPlus/api/state.py` | 상태 객체 관리 |

설치 폴더에서는 `pyenergyplus` 패키지 형태로 제공됩니다.

### 기본 실행 패턴

```python
import sys
sys.path.insert(0, r"C:\EnergyPlusV26-2-0")
from pyenergyplus.api import EnergyPlusAPI

api = EnergyPlusAPI()
state = api.state_manager.new_state()
api.runtime.run_energyplus(state, [
    "-d", r".\out\case_01",
    "-w", r".\weather.epw",
    r".\model_01.idf",
])
```

### 콜백 — 시뮬레이션 중간에 개입하는 지점

`runtime.py` 에 **20개 이상의 콜백 등록 함수**가 있습니다.
이것이 2-4절 호출 계층도의 각 단계에 대응합니다.

| 콜백 | 개입 시점 |
|---|---|
| `callback_begin_new_environment` | 환경(설계일/연간) 시작 시 |
| `callback_after_new_environment_warmup_complete` | **Warmup 수렴 완료 직후** |
| `callback_begin_zone_timestep_before_init_heat_balance` | 존 타임스텝 시작, 열평형 전 |
| `callback_after_predictor_before_hvac_managers` | **부하 예측 후, 설비 계산 전** ← 제어로직 삽입 지점 |
| `callback_inside_system_iteration_loop` | 설비 반복계산 내부 |
| `callback_end_zone_timestep_after_zone_reporting` | 존 타임스텝 종료 후 |
| `callback_end_zone_sizing` / `callback_end_system_sizing` | **사이징 완료 직후** ← 용량 자동조정 지점 |
| `callback_register_external_hvac_manager` | 설비 시스템 전체를 외부 코드로 대체 |
| `callback_progress` / `callback_message` | **진행률·메시지 수신** ← 웹 UI 진행표시에 활용 |

### 데이터 교환 — 읽고 쓸 수 있는 것

`datatransfer.py` 기준:

| 종류 | 함수 | 설명 |
|---|---|---|
| 출력변수 | `get_variable_handle` → `get_variable_value` | 센서처럼 값 읽기 (사전에 `request_variable` 필요) |
| 계량기 | `get_meter_handle` → `get_meter_value` | 에너지 사용량 누적값 |
| **액추에이터** | `get_actuator_handle` → `set_actuator_value` | **값을 써서 모델을 조작** |
| 내부변수 | `get_internal_variable_handle` → `get_internal_variable_value` | 내부 계산값 |
| 구성체 | `get_construction_handle` | 벽체 구성 핸들 (동적 외피 모사) |
| 전역/EMS | `get_global_value` / `set_global_value` 등 | EMS 변수 |
| 시간 정보 | `year` / `month` / `day_of_month` / `hour` / `current_time` / `sun_is_up` 등 | 현재 시점 |
| 추세 | `get_trend_average` / `get_trend_min` / `get_trend_max` 등 | 과거 이력 통계 |
| 진단 | `api_data_fully_ready`, `api_error_flag`, `list_available_api_data_csv` | **사용 가능한 핸들 목록 덤프** |

> **입문 팁**: `list_available_api_data_csv()` 를 먼저 호출해 CSV로 덤프하면
> 그 모델에서 읽고 쓸 수 있는 모든 항목의 정확한 이름을 확인할 수 있습니다.
> 핸들 이름을 추측하다 시간을 버리지 말고 이것부터 하십시오.

### 주의: 액추에이터는 "모델 조작"입니다

`set_actuator_value` 로 설정온도·창문개방·조명출력 등을 실시간 변경할 수 있습니다.
강력하지만, **물리적으로 불가능한 값을 넣어도 엔진은 그대로 계산합니다.**
VE 검토 결과로 쓸 때는 입력 범위 검증을 직접 해야 합니다.

## 4-6. 권장 파이프라인 설계

```
[1] 기준 모델 (baseline.epJSON)
         │
[2] 케이스 생성기  ── 변수 조합(단열두께 × 창호U값 × 설비효율 …)
         │            epJSON 키 수정 → case_001.epJSON … case_NNN.epJSON
         │            (→ 03-입력스키마.md)
[3] 병렬 실행기  ── CPU 코어 수 - 1 만큼 동시 실행
         │            케이스별 -d / -p 분리 필수
[4] 성공 판정  ── .end / .err / Warmup / Unmet Hours  (4-4절)
         │            실패 케이스는 결과에서 제외하고 별도 리포트
[5] 결과 수집  ── eplusout.sql 에 SQL 질의 → 단일 결과 테이블
         │
[6] 비교·시각화  ── 1차에너지소요량, 에너지자립률, 투자비 대비 절감액(VE)
```

**단계별로 중간 산출물을 파일로 남기십시오.**
케이스 100개를 2시간 돌린 뒤 [5]에서 실수를 발견하면
[1]~[4]를 다시 돌리지 않고 재집계만 할 수 있습니다.
EnergyPlus 자동화에서 가장 비싼 자원은 **계산 시간**입니다.
