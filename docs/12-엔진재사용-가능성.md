# 12. 엔진 재사용 가능성 — 별도 툴 제작을 위한 조사

> **이 문서의 범위**: EnergyPlus 측면만 다룹니다. ECO2 결합이나 통합 설계는
> 별도 프로젝트에서 진행합니다. 여기 적힌 것은 "EnergyPlus에서 무엇을 가져올 수
> 있는가"에 대한 **실측 조사 결과**입니다.
>
> 측정 기준: `v26.2.0` 태그, `src/EnergyPlus/` 각 `.cc` 파일

---

## 12-1. 결론 먼저

EnergyPlus는 **"떼어낼 수 있는 부분"과 "못 떼는 부분"이 뚜렷하게 갈립니다.**

| 성격 | 특징 | 재사용 |
|---|---|---|
| **물성·수학 커널** | 의존성 6~12개. 입력을 받아 값을 돌려주는 순수 계산 | ✅ 가능 |
| **통합 오케스트레이션** | 의존성 38~63개. 시뮬레이션 전체 상태를 참조 | ❌ 사실상 불가 |

즉 **"가장 어려운 물리 계산은 재사용하고, 조립은 새로 한다"** 가 현실적인 길입니다.

열평형을 돌리는 관리자 코드(`HeatBalanceSurfaceManager`, `ZoneTempPredictorCorrector`,
`HVACManager`)는 가져올 수 없습니다. **그 부분은 직접 설계해야 합니다.**

## 12-3. 가장 가치 있는 재사용 후보

### `Construction.cc` — CTF 계산 (2,110줄 / 의존성 7)

EnergyPlus에서 **물리적으로 가장 어렵고 가치 있는 부분**인데 의존성이 가장 적습니다.

- 실제 의존성 7개 중 물리와 무관한 것(`DisplayRoutines`, `OutputReportPredefined`,
  `UtilityRoutines`)을 빼면 핵심은 `Material`, `DataConversions` 둘
- `state.` 접근이 **45회뿐** — 전역 상태에 거의 의존하지 않음
- 알고리즘: Seem(1987) 상태공간법. 상세는 [`06-CTF상세.md`](06-CTF상세.md)

> 벽체 동적 열응답을 처음부터 구현하는 것은 매우 어렵습니다. 이 모듈을 가져오면
> **1~2개월 작업을 수일로 줄일 수 있습니다.**

### `Psychrometrics.cc` (1,466줄 / 의존성 7)

습공기 함수는 건물에너지 툴의 기반입니다. 직접 구현하면 미묘한 오차와
수렴 문제에 시달립니다. 30년 검증된 구현을 쓰는 것이 합리적입니다.

### `FluidProperties.cc` (6,982줄 / 의존성 6)

물·글리콜·냉매 물성. 설비 계산에 필수이고, 데이터 테이블이 포함되어 있어
직접 만들기 어렵습니다.

## 12-4. 규모 사다리 — 어디까지 만들 것인가

EnergyPlus는 **1996년부터 30년, 75.9만 줄**입니다. 전체 재현은 비현실적입니다.
범위를 정하는 것이 첫 결정입니다.

| 수준 | 방법론 | 예상 규모 | 성격 |
|---|---|---:|---|
| 1 | 월별 준정상 (ISO 13790 계열) | 수백~2천 줄 | 가장 빠름. 축열·제어 효과는 간이 보정 |
| 2 | **시간별 RC 모델** (ISO 52016-1, 5R1C) | 2~5천 줄 | 동적. 상용 도구 다수가 이 방식 |
| 3 | **CTF 기반 동적** | 1~3만 줄 | `Construction.cc` 이식. EnergyPlus 수준 정밀도 |
| 4 | 전체 EnergyPlus급 | 75만 줄 | 비현실적 |

**설비 상세도가 규모를 좌우합니다.** EnergyPlus처럼 코일·팬·플랜트를 개별
모델링하면 폭발합니다(`UnitarySystem` 하나가 18,430줄). 효율·COP·부분부하 곡선
기반 간이 모델이면 수천 줄로 끝납니다.

## 12-5. 라이선스 — 코드를 가져올 때

BSD 3-Clause 계열이라 **수정·재배포·상업적 이용이 모두 허용**됩니다.
다만 `LICENSE.txt` 에 일반 BSD에 없는 **제4항**이 있습니다.

| 의무 | 내용 |
|---|---|
| 저작권 표시 유지 | 가져온 파일의 저작권·면책 조항을 그대로 남길 것 |
| **명칭 제한** | 회사명·제품명·광고에 `EnergyPlus`·`E+`·`e+` 또는 유사 명칭을 **DOE 사전 서면 동의 없이 사용 불가** |
| 단독 배포 시 표기 | 수정 없이 배포하거나 소프트웨어 부분만 지칭할 때는 `"EnergyPlus version X" software` 형식 |

> **제품화 시 가장 주의할 점**: 서비스명·제품명에 EnergyPlus를 쓸 수 없습니다.
> 독자 명칭을 쓰고, 기능 설명란에만
> "EnergyPlus version 26.2.0 software 의 계산 모듈 일부를 사용합니다" 처럼
> 적는 방식이 안전합니다.
>
> 법률 자문이 아닙니다. 상용화 전 별도 검토를 권합니다.
> 상세는 [`README`](../README.md) 결론 (2).

### `third_party/` 는 별도 라이선스입니다

가져오려는 모듈이 `third_party/` 를 의존하면 **그 라이브러리의 라이선스를
따로 확인**해야 합니다.

| 모듈 | 의존 라이브러리 |
|---|---|
| `PVWatts` | `ssc` (NREL SAM) |
| `WindowManager` | `Windows-CalcEngine` (LBNL) |
| `HeatBalanceKivaManager` | `kiva` |
| `SolarShading` | `penumbra` (GPU 음영) |
| 다수 | `ObjexxFCL` (Fortran 호환 배열 — 이식 시 걸림돌) |

> **`ObjexxFCL` 주의**: EnergyPlus는 원래 Fortran 코드를 C++로 옮긴 것이라
> Fortran식 1-based 배열 라이브러리를 씁니다. 모듈을 가져오면 이것도 따라옵니다.
> 현대적 C++/다른 언어로 재작성할 때 가장 번거로운 부분입니다.

## 12-6. 직접 설계해야 하는 부분

재사용으로 해결되지 않는, **반드시 새로 만들어야 하는 것**들입니다.

| 영역 | 왜 못 가져오나 | 참고 문서 |
|---|---|---|
| **존 열평형 조립** | `ZoneTempPredictorCorrector` 의존성 44 | [`10`](10-에너지분석로직.md) 1-2절 Predict/Correct |
| **표면 열평형 조립** | `HeatBalanceSurfaceManager` 의존성 63 | [`02`](02-계산엔진.md) 2-4절 호출 계층도 |
| **설비 조립** | `HVACManager` 의존성 50 | [`10`](10-에너지분석로직.md) 3-2절 4계층 구조 |
| 시간 루프·Warmup | 전체 구조에 걸침 | [`02`](02-계산엔진.md) 2-2·2-3절 |
| 입력 스키마 | 877객체는 과도. 자체 설계 필요 | [`03`](03-입력스키마.md) |
| 출력 체계 | 33종은 과도. 자체 설계 필요 | [`04`](04-자동화.md) 4-3절 |

**다행인 점**: 이 "조립" 부분의 **설계 논리는 이미 이 저장소에 정리되어 있습니다.**
코드는 못 가져오지만 **무엇을 어떤 순서로 해야 하는지는 문서화**되어 있습니다.

## 12-8. 이 조사의 한계

- **의존성 개수는 이식 난이도의 대략적 지표**입니다. 개수가 적어도 특정 헤더가
  무겁게 얽혀 있을 수 있고, 많아도 대부분 데이터 구조체면 쉬울 수 있습니다.
  실제 이식 전에 대상 모듈의 헤더를 직접 읽어 확인하십시오.
- **빌드·실행으로 검증하지 않았습니다.** 이 세션에서는 외부 저장소 코드 빌드가
  차단되어 있어 "실제로 떼어내 컴파일되는지"는 확인하지 못했습니다.
- **ECO2 측면은 다루지 않았습니다.** 통합 설계는 별도 프로젝트의 몫입니다.
